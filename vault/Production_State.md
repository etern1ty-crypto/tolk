## Домен и поддомены

Основной адрес — **tolkmessenger.ru** (переехали с cleanvp.ru 26.07.2026;
старый домен отвечает и переадресует с сохранением пути, поэтому разосланные
приглашения живы).

Поддомены заработали 27.07.2026: в reg.ru стоит wildcard-запись `*`, сертификат
Let's Encrypt покрывает семь имён, продление автоматическое.

| Имя | Что делает | Проверено |
|---|---|---|
| `tolkmessenger.ru` | приложение | 200 |
| `www` | переадресация на апекс | 301 |
| `api` | шлюз отдельным именем, для мобильного приложения | 200 |
| `ws` | веб-сокет | — |
| `media` | файлы, без печений, вечный кэш | 404 на корень (верно) |
| `s` | короткие ссылки: `s.tolkmessenger.ru/abc` → `/s/abc` | 301 |
| `status` | живость службы | 200 |

Браузер намеренно ходит в API **того же origin**, а не в `api.` — так каждый
вызов экономит предварительный запрос CORS. Отдельное имя нужно нативному
приложению, которому CORS не мешает; в клиенте для этого уже есть
`VITE_API_URL` и `VITE_WS_URL`.

Произвольное имя под доменом (`что-угодно.tolkmessenger.ru`) даёт ошибку
сертификата, а не 404: wildcard-запись в DNS ведёт запрос к нам, но в
сертификате такого имени нет. Приложение под чужим именем при этом не
отдаётся — то есть цель достигнута. Чтобы получить чистый 404, понадобился бы
wildcard-сертификат, а он требует проверки через DNS и токена API reg.ru;
ради имён, которыми никто не пользуется, это не стоит усложнения.

## Единственное, что сломано

**Google Drive.** 111 файлов из 114 вынесены в Drive старым ночным скриптом на
Node — он двигал всё старше двух суток независимо от того, кончается ли место.
Токен доступа отозван, поэтому файлы недостижимы. Локально осталось три.

Чинится только со стороны Google: опубликовать приложение в консоли (сейчас
режим «Testing», в нём ключ живёт 7 дней) и выпустить новый
`DRIVE_REFRESH_TOKEN`. Пока не сделано — вместо битой иконки показывается
«Фото недоступно», и лента остаётся читаемой.

Нынешний выгрузчик так себя не ведёт: он смотрит на занятое место и при
бюджете 8 ГБ против 14 МБ медиа не запускается вовсе.

## Почему функция может «быть» и не работать

Три отдельных места, где след обрывается молча:

1. **nginx не проксирует путь.** Список путей написан руками и отстал от кода:
   `/echoes` и `/messages` уходили в SPA, и сервер отвечал `200` с HTML. Теперь
   расхождение роняет сборку — тест `routes_proxy_test.go`.
2. **Клиент не зовёт готовый маршрут.** Так было с Echo, блокировками и
   жалобами: сервер умел, кнопки не существовало.
3. **Клиент делает вид.** Удаление сообщения меняло только своё состояние —
   выглядело сработавшим, у собеседника оставалось.

При проверке функции стоит пройти все три, а не только последний.
